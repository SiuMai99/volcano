# Pending GPU 作业的节点间碎片化诊断开发计划

> 状态：三个叠加 PR 的开发计划，首版实现已提交，待审查合并
>
> 依据：[需求](gpu-pending-fragmentation-diagnosis-zh.md)与[设计方案](gpu-pending-fragmentation-design-zh.md)
>
> 首版交付：对证据充分的单 Pod 整卡 `nvidia.com/gpu` 放置失败，在既有调度失败消息中输出节点间碎片诊断

## 1. 开发原则与首版边界

按“证明候选节点 → 计算空闲量 → 附加诊断消息”的顺序开发。**不能先实现 `sum(Node.Idle.GPU)` 再补其他约束**：当前 `allocate` 先用 `FutureIdle` 做资源检查，资源不足时不会继续运行后面的插件谓词，因此现有 `Insufficient nvidia.com/gpu` 不能证明该节点满足 CPU、亲和性、污点等条件。

首版只处理已进入正常 `allocate` 节点检查、请求正整数整卡 `nvidia.com/gpu`、最终仍为 Pending 的单 Pod。先以**不带显式网络拓扑约束的普通节点范围**为交付目标；网络拓扑域多轮试探、跨调度分片的合并诊断、Gang 整体可调度性，以及 vGPU／MIG／DRA／GPU 共享均暂缓。硬分片模式只有在能证明本调度器负责的节点范围完整时才可启用，否则回退原有原因。

初次落地采用 `allocate` 的显式开关，默认关闭；在已验证的调度配置中开启。该开关只控制诊断，不改变过滤、排序、抢占或绑定。后续是否默认开启，以性能和误报验收结果决定。

## 2. 当前代码基线与预计落点

| 当前事实 | 对开发的影响／预计落点 |
| --- | --- |
| `allocateResourcesForTasks` 在队列和前置检查后调用 `PredicateNodes`；`allocate.predicate` 先比较 `FutureIdle`，不足时提前返回 | 只在真实放置失败后触发诊断；必须补齐非 GPU 约束证据，不能直接解析已有资源错误当作证明。主要落点：`pkg/scheduler/actions/allocate/allocate.go` |
| `PredicateNodes` 可在找到足够可行节点后提前停止，并支持谓词错误缓存；Session 按插件顺序在首个失败处返回 | 诊断需要覆盖完整相关节点集，不把正常放置的采样、缓存命中或早退当作完整证据。预计需要明确的只读诊断入口，而非复用正常过滤结果作为全集 |
| 默认配置启用 `predicates`；该插件组合多个 Kubernetes Filter，另有自定义插件可注册 Predicate | 先列出实际启用插件及其 GPU 依赖、读写副作用、缓存／CycleState 依赖；每个启用约束都有可靠诊断路径时才可输出确定结论 |
| `JobInfo.NodesFitErrors` 供 `TaskSchedulingReason` 读取，随后 `RecordJobStatusEvent` 写 Pod 条件和事件；在不同拓扑域试探前可能重置失败信息 | 诊断证据应随本次最终失败结果进入既有原因通道；不能在中间试探阶段发布，也不能让一次被丢弃的试探结论泄漏到最终消息 |
| `NodeInfo.Idle` 表示当前空闲量，`FutureIdle` 还包含释放中、扣除已 Pipelined 的资源 | 碎片数值从该 Pod 检查时的会话 `Idle` 读取；已分配或 Pipelined 时不输出诊断 |

这些是本地源码中的现状与**拟定**落点，不代表已经存在非 GPU 诊断接口。

## 3. 分阶段任务与验收门槛

### 阶段 0：冻结可证明的支持范围

**工作**

1. 列出首版配置中全部启用的 PrePredicate／Predicate 及 Kubernetes Filter，按“与 GPU 容量无关、依赖 GPU 或共享设备状态、可能改变状态、尚不确定”分类；核对 NodeInfo、Pod、CycleState、插件缓存是否可供只读检查。
2. 用最小模拟会话验证：在 `FutureIdle` 因 GPU 不足提前返回时，能否在不改变正常调度状态的前提下，得到该节点所有其他约束的可靠结论。覆盖节点选择／亲和性、污点、CPU／内存及至少一个自定义插件或不支持插件。
3. 冻结首版“支持配置清单”和回退规则。任何已启用的 Predicate 无法被可靠评估时，本轮不输出确定诊断；不得简单跳过该插件。

**通过条件**：形成可复现的正例 1／2／1 请求 4，以及“GPU 不足且 CPU 或亲和性失败”的反例；证明诊断前后正常过滤结果、插件状态与 Pod 内容一致。若默认配置无法满足此门槛，先收窄到明确可支持的配置，不能以不完整的结论发布。

### 阶段 1：只读证据收集与判定

**工作**

1. 在 Pod 的正常节点放置尝试失败后，按同一会话中该 Pod 当时的状态检查完整相关节点集。对每个节点记录“其他约束通过／失败／无法判定”和当前空闲整卡数；不使用实时 Node、物理设备利用率或下一轮快照。
2. 明确禁止触发条件：未进入节点检查、PrePredicate／队列检查失败、已找到放置或等待释放资源的结果、节点集不完整、插件错误、预算耗尽、资源数值异常、域／分片归属不清。
3. 在所有相关节点可判定的前提下，计算请求量 `R`、候选数 `N`、`sum(Fi)` 和 `max(Fi)`；只有 `N>0 && sum(Fi)>=R && max(Fi)<R` 且没有冲突原因时产出诊断结论。判定本身不修改调度对象、错误缓存或插件状态。

**通过条件**：表驱动测试覆盖等号边界、总量不足、单节点足够、无候选节点、其他约束失败、未知插件／节点、`Idle` 与 `FutureIdle` 不同、零值与异常值；负例均保留原有原因。测试还要证明完整节点覆盖及同一 Pod 检查时刻的数值口径。

### 阶段 2：接入失败信息并控制输出

**工作**

1. 仅在最终仍 Pending 且该 Pod 的正常放置失败已确定时，将阶段 1 的结论接入已有 Task 失败原因；在 Job 或 SubJob 的多次试探、重置和回滚后只保留最终有效结论。
2. 在 Pod `PodScheduled=False` 条件和 `FailedScheduling` 事件的消息中输出请求量、候选节点数、合计空闲量、单节点最大空闲量。Pod 条件 `Reason` 保持 `Unschedulable`，事件 `Reason` 保持 `FailedScheduling`；PodGroup 仍只汇总成员原因，不赋予整个 Gang 碎片结论。
3. 保留更直接的准入、Gang、插件错误或绑定失败原因。证据缺失、开关关闭或不支持配置时，沿用原有消息。不建立额外的周期性事件通道。

**通过条件**：状态与事件均出现预期消息；关闭开关和所有负例的原因不变；已分配／Pipelined 的 Pod 不带诊断；同样的失败状态重复周期不新增同内容事件，资源状态改变时可更新消息且下一轮重新判定。

### 阶段 3：端到端验证与交付

**工作**

1. 在模拟节点的调度测试中复现 1／2／1 请求 4，并覆盖 CPU／亲和性／污点、队列准入、Gang、拓扑约束和不支持配置的回退路径；比较启用前后的放置与绑定结果。
2. 测量诊断仅在失败路径执行时的开销；为节点扫描设定可观测的上限或预算，超过预算必须回退，不能拖慢正常调度。检查失败消息长度与事件数量。
3. 更新用户文档：开关、支持的调度配置、消息含义、证据不足时为何不显示、模拟测试与真实设备分配的区别。

**通过条件**：范围内正例能稳定输出；负例无误报；Pod／PodGroup 原有语义和调度结果不变；性能与事件行为可接受。模拟测试不宣称已证明 kubelet DeviceID 或 GPU UUID。

## 4. 建议的提交／PR 边界

| 交付 | 内容 | 合入门槛 |
| --- | --- | --- |
| PR 1：证据能力 | 支持范围清单、只读诊断入口和候选节点证明；保持输出关闭 | 阶段 0、1 的正反例和无副作用证明通过 |
| PR 2：消息接入 | `allocate` 失败结果接线、开关、Pod 消息及 PodGroup 边界 | 阶段 2 测试通过，关闭开关行为与原来一致 |
| PR 3：验收与文档 | 模拟节点端到端场景、性能／事件核对、配置与运维说明 | 阶段 3 全部通过；若证据范围仍不完整，则只交付明确受限的配置 |

PR 2 不扩展到抢占、迁移、Reservation、descheduler 或新的 PodGroup API。每个 PR 保持可独立审查；若阶段 0 发现可靠诊断必须改动大量通用谓词接口，先更新设计和支持范围，再决定是否继续，而不降低“证据充分”的标准。

## 5. 最终验收清单

- [ ] 正例：3 个候选节点空闲 1／2／1，单 Pod 请求 4，消息为 `R=4、N=3、sum=4、max=2`。
- [ ] 反例：总量 3、某节点空闲至少 4、CPU／亲和性／污点失败、未知插件、节点集缺失、等待释放资源、未准入或仅 Gang 未就绪，都不误报。
- [ ] 证据覆盖该 Pod 本轮的完整相关节点集，且资源数值来自同一会话中的同一检查时刻。
- [ ] 开关关闭和不支持配置时，调度结果与既有失败原因不变。
- [ ] `PodScheduled` 原因仍为 `Unschedulable`；PodGroup 没有整体碎片化结论；重复周期没有额外同内容事件。
- [ ] 聚焦测试、调度相关测试和 `git diff --check` 通过；模拟结果的设备级证明边界写入交付说明。
